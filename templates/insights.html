The Defense-in-Depth Model for Web Applications

Why application code security alone is never enough.

Modern web security relies on defense-in-depth. Even if a developer uses modern web frameworks with built-in protections against SQL injection or template escaping, a single overlooked parameter or third-party script can introduce vulnerabilities.

HTTP security headers act as client-side guardrails. When a web server returns proper headers (such as CSP, HSTS, and X-Content-Type-Options), it instructs the user's browser to enforce strict operational rules—rendering entire categories of attacks inert even if an injection vulnerability exists in the backend code.

Layer 1

Transport Encryption (TLS/HTTPS)

Protects data across the network wire. Defends against packet sniffing, Wi-Fi eavesdropping, and ARP cache poisoning.

Layer 2

Browser Boundary Hardening

HSTS, CSP, X-Frame-Options, and Referrer-Policy enforce strict execution constraints inside the client browser runtime.

Layer 3

Session & Cookie Isolation

HttpOnly, Secure, and SameSite attributes ensure session tokens cannot be stolen via XSS or forged via CSRF.

Layer 4

Domain & DNS Governance

CAA records and SPF/DMARC specify which Certificate Authorities and mail servers are authorized on behalf of the domain.

The ConfigScore Scoring Algorithm

Transparent, objective, and reproducible evaluation mechanics.

ConfigScore uses a deterministic deduction model. Every audited website begins with a perfect baseline score of 100 points. Points are subtracted based on the severity and criticality of any missing or improperly configured defensive controls:

Severity Tier Point Deduction Security Controls Included Rationale
Critical -10 to -15 pts HTTPS, Valid Certificate, Modern TLS Protocol, Content Security Policy Fundamental transport integrity or primary defense against code execution.
High -6 to -8 pts HSTS, X-Frame-Options, Secure Cookies, HttpOnly Cookies, CORS Credentials Direct exposure to session hijacking, clickjacking, or SSL-stripping.
Medium -4 to -5 pts X-Content-Type-Options, Referrer-Policy, SameSite Cookies, DNS CAA Records Protection against MIME-confusion, cross-site CSRF, and referrer leakage.
Low -1 to -3 pts Permissions-Policy, Server Disclosure, Cache-Control Minimizes device API access, reconnaissance fingerprinting, and cache retention.
90 – 100 Low Risk

Well-hardened configuration following modern security best practices.

70 – 89 Medium Risk

Satisfactory baseline, but missing specific defense-in-depth headers.

40 – 69 High Risk

Multiple important protections missing; immediate remediation advised.

0 – 39 Critical Risk

Severely exposed to active network eavesdropping, MitM, or framing.

03

Production Website Security Checklist

10 essential configuration steps before deploying any website to production.

1
Enforce HTTPS with Automated Renewal:

Configure Let's Encrypt with Certbot cron or cloud ACM so certificates renew automatically at least 30 days before expiration.

2
Disable Obsolete TLS Protocols:

Set web server configuration to support only TLS 1.2 and TLS 1.3. Explicitly disable SSLv2, SSLv3, TLS 1.0, and TLS 1.1.

3
Activate HTTP Strict Transport Security (HSTS):

Send Strict-Transport-Security: max-age=31536000; includeSubDomains to stop SSL-stripping.

4
Block Clickjacking with Frame Restrictions:

Deploy X-Frame-Options: DENY and CSP frame-ancestors 'none' on sensitive pages.

5
Prevent MIME-Type Sniffing:

Always declare X-Content-Type-Options: nosniff to prevent browsers from executing polyglot uploads.

6
Control Referrer Leakage:

Use Referrer-Policy: strict-origin-when-cross-origin so query parameters are not transmitted to third parties.

7
Harden Session Cookies:

Set Secure, HttpOnly, and SameSite=Lax (or Strict) on all authentication cookies.

8
Suppress Server Fingerprints:

Turn off server_tokens in Nginx and disable X-Powered-By in Express/PHP.

9
Publish DNS CAA Records:

Restrict certificate issuance in your DNS provider zone to only your designated Certificate Authority.

10
Craft a Phased Content Security Policy:

Start with CSP in Report-Only mode, eliminate inline scripts using nonces, and then switch to enforcing mode.
